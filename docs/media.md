# Media, clocks, and capture decision

Engineering experiment: FFmpeg 8.1.3 generated a numbered 12-second VP9/Opus fixture. Integration tests ingest a real generated 4-second recording, retain it across a SQLite close/reopen, render [1,3), probe two-second output, and render/probe portrait with approved captions. This verifies real media processing; it does not verify microphone capture, OBS mute behavior or audible human speech.

Decision: implement a narrow browser screen/tab capture and finalized OBS import first. Browser selection exposes exactly what the user chose and requires a shared audio track. OBS remote control would require a separately configured OBS instance and credentials, so it is not implemented speculatively. OBS WebSocket support exists upstream, but no OBS experiment ran here. Device permission, audio-route availability and A/V sync are pending human checks. Supported tested media is WebM VP9/Opus; MP4/MKV support depends on local decoders. Fedora's FFmpeg may lack H.264 decoding; import a WebM recording if probe/decode fails.

Browser capture uses MediaRecorder with roughly 1.5-second data events, but does not assume timeslice timing is exact. Each chunk has an immutable sequence/hash, browser elapsed time, BlobEvent timecode and server receive timestamp. Chunks are flushed and promoted before their metadata/acknowledgment commits. Retries use the same sequence and bytes; changed retries or missing sequences fail. The upload backlog is capped at 16 MB and individual chunks at 8 MB. Backpressure/device loss ends the epoch rather than silently bridging a gap. MediaRecorder's data events are not individually playable files: the adapter joins bytes from one epoch and FFmpeg remuxes them into a finalized owned asset.

One epoch permits one hour / 220 MB, with at most 512 MB of unresolved chunk data across captures and five interrupted epochs. Finalized source storage remains 200 files / 5 GB. No automatic rolling eviction or epoch rotation is implemented. The beginning of a long exchange is retained because all acknowledged chunks remain protected until finalization/discard. A live “Save that exchange” snapshot owns its complete acknowledged source; its default last-30-second suggestion is a manual starting point and can be expanded (approved intervals remain ≤180 seconds). Snapshots reuse stable operation keys after interrupted linkage rather than silently selecting a different source.

On reload/restart, the epoch becomes recoverable/interrupted and its unacknowledged tail is explicitly unknown. Recovery never claims to reconstruct unreceived data. A finalized media asset is validated before the session references it. Finished/discarded raw chunk files may then be removed; immutable sources used by drafts are separate and remain protected. Backups include acknowledged chunks for pending epochs and verify their hashes. Orphan/temp files from an OS kill still require maintenance; graceful error paths clean their scratch files.

Time conventions: chat receivedAt remains a Twitch envelope time or manual creation time. Capture clientWallAt and clientMonotonicMs anchor the client setup request; browser elapsed/timecode values are recorded independently from server arrival. These do not prove when a spoken response reached the broadcast. Finalized-media presentation timestamps remain authoritative for trims. Each capture is a separate epoch; no interpolation across restarts, pauses or source changes. Media intervals are half-open [start,end); captions are seconds relative to that interval, ordered and contained. Audio/video synchronization and broadcast-delay calibration require real capture acceptance.

Rendering decodes/re-encodes into a separate WebM. The source is never served as a public file with client-side seek bounds. Private lead-in preview does not extend publication. Portrait uses only approved derived media, original message and approved captions. Full source frame is fitted into 720×1280 rather than cropped. Message limit for portrait is 400 characters; longer context remains in the replay page. Word timing, variable-frame-rate edge cases, exact human syllable boundaries and real audio sync require further tests.

Local transcription: install/build [whisper.cpp](https://github.com/ggml-org/whisper.cpp), select a model, set WHISPER_BIN and WHISPER_MODEL to absolute server-side paths. UI queues analysis of the exact saved interval (at most 180 seconds), even late in a long file, with two CPU threads and a five-minute inference timeout. FFmpeg extracts only that interval; provider millisecond offsets are converted into source-media seconds. Jobs have persisted attempt counts, an eight-minute lease marker and generation fencing; startup recovers abandoned work under the exclusive process owner. One job runs at a time, queue capacity ten, maximum three automatic attempts with backoff. Cancellation signals local subprocesses and fences late results. Invalid timings/output fail privately rather than becoming captions. Completed transcripts retain source revision, interval, provider/model label and validation provenance. Results cannot be silently applied to a different revision. JSON offsets are validated and divided from milliseconds into seconds. No fabricated word timing. No audio leaves this machine, no API charges. Model installation, ASR accuracy and latency are unverified here. Caption corrections create a new draft revision; original transcript is retained with source revision provenance.

Preserve `.data/media` with the database. No automatic retention deletion is enabled. Missing/corrupt files fail processing or playback; choose another source or restore a verified backup. Crash-orphan files may be retained for inspection; stop app before manual cleanup. Hardware impact, 60-minute memory bounds, disk-full injection and real mute/device-loss scenarios are pending.

Official capture references checked for this slice: [MediaRecorder data events](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/dataavailable_event), [BlobEvent timecode](https://developer.mozilla.org/en-US/docs/Web/API/BlobEvent/timecode). Browser tests exercise actual MediaRecorder output from a labelled generated canvas and sine tone. Provider tests use a fixture CLI, not a speech model. Neither is a live-device or real-ASR acceptance claim.
